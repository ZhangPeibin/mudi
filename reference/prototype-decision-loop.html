可验证原型：决策闭环速查

目标不是“做个 demo”，而是用最少代码取得足以关闭一个问题的证据。

六步闭环

  1. Question只写一个能被证伪的问题。
  2. Evidence先定义什么结果足以回答它。
  3. Fixture覆盖正常、边界和最坏场景。
  4. Runner提供一个无需思考的运行命令。
  5. Review机器查不变量，人查意义和体验。
  6. Verdict确认、调整或拒绝；写回持久文档。

开始前

  • 这个问题还没有答案吗？如果已经确认，就不需要原型。
  • 原型的失败结果会改变什么决定？如果什么都不改变，问题可能不值得原型。
  • 哪些条件必须固定，才能让两次结果可比较？
  • 代码放在哪里最接近上下文、又最不容易被误认成生产实现？

完成标准

必须留下应该删除
问题、证据、结论临时状态模型
更新后的 PRD / ADR / issue假数据和原型路由
必要的评审 fixture只为试验存在的交互胶水
生产实现需要遵守的不变量未按生产标准设计的抽象

常见失败模式

  • 问题过大：“做一版新 UI 看看”，没有明确判定条件。
  • 数据太友好：短名字、无 N/A、无溢出，边界问题被隐藏。
  • 只有自动检查：字符串都在，但层级和可读性已经坏掉。
  • 只有截图：看起来不错，但交互和恢复行为没有被验证。
  • 没有结论：原型留在仓库里腐化，下一次又从头讨论。
  • 直接升产：把为速度写的代码误当成长期架构。

一句话检查

在开始编码前补完这句话：

“我要用 ______ 场景，在 ______ 条件下，观察 ______，从而决定 ______。”

如果四个空无法具体填写，先别写原型。
