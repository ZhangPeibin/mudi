## 1. 结论

v2.0.1 当前不应继续增加 Checkpoint 实现。阻塞点不是实现速度，而是以下边界尚未
稳定：

1. 权威数据没有统一的 Schema Owner 和版本契约。
2. Observation 与会修改权威状态的 Reconciliation 混在同一个 Refresh 周期中。
3. Application 同时依赖 Presentation 类型和具体系统 Adapter，依赖方向不成立。
4. Managed Session 的领域规则、应用流程、SQLite、进程、tmux 和 Terminal.app
   实现位于同一模块。
5. TUI 以不断增加的并行 `Option<ModalState>` 和全局按键分支承载新工作流。
6. Checkpoint 的持久化、证据、字段权限、保留策略和 Handoff 交互仍未决定。

本计划采用以下总体路线：

> 先建立持久化和依赖边界，再分离 Observation 与 Reconciliation，然后拆解
> Managed Session 和 TUI，最后才允许 Checkpoint 进入实现。

不进行一次性大重写，不维护重构前本地数据格式的运行时兼容代码，也不为了未来能力
提前引入通用工作流框架。

## 2. 审计基线

以下事实用于判断计划是否解决了实际问题，而不是只移动文件：

- `src/application/managed_sessions.rs` 同时拥有领域记录、Binding、New/Resume、
  SQLite、进程、tmux 和 Terminal.app 逻辑。
- `src/application/observation/refresh.rs` 名义上发布只读 Snapshot，实际还会推进
  Binding、关联 Title、同步 Session Metadata 和清理运行环境。
- `src/application/mod.rs` 直接依赖 `presentation::tui::{Ui, UiIntent}`、Clipboard
  和具体 macOS 通知实现。
- `src/presentation/tui/mod.rs` 直接持有并写入权威 Session Metadata。
- `TaskStore` 与 `ManagedLaunchStore` 各自通过运行时表结构探测和零散 `ALTER TABLE`
  演进，没有统一的 Schema Version。
- 现有 Managed Store 的 legacy 测试并未从上一版真实 Schema 建库，因此没有覆盖
  `project_kind NOT NULL` 等旧约束，完整测试通过仍发生真实升级失败。
- v2.0.1 范围记录仍将 Checkpoint 的关键持久化和交互契约列为开放设计决策。

## 3. 目标与非目标

### 3.1 目标

- 建立可以被代码结构和测试共同验证的单向依赖。
- 为所有 Mudi 权威元数据建立一个 Schema Owner、一个版本号和明确事务边界。
- 让 Observation 可独立执行且绝不修改权威状态。
- 让 Reconciliation 只能推进已存在、已授权的状态，不能创造授权。
- 让每个应用工作流拥有独立的输入、输出、错误和端口，而不是扩大全局 Controller。
- 保留 Handoff 已有的安全、隐私、显式授权和失败安全行为。
- 让 v2.0.1 后续能力可以作为垂直切片加入，而不是同时修改所有中心模块。

### 3.2 非目标

- 本计划不实现 Checkpoint。
- 不引入通用 Event Bus、CQRS 框架、插件系统、工作流引擎或依赖注入框架。
- 不把 New、Resume、Handoff 强行抽象成一个含糊的通用 Task。
- 不改变 Provider-native Session ID、Current Run、Managed Session、Operation Task 或
  Handoff 的领域含义。
- 不改变 ADR 0002 至 0007 定义的授权、安全、Artifact 和 Successor 规则。
- 不为重构前的本地数据库编写长期兼容分支或逐版本迁移链。
- 不以文件行数下降作为成功标准。文件拆分必须对应职责和依赖边界变化。

## 4. 必须保持的约束

整个重构期间，下列规则不可暂时放宽：

- Provider source JSONL 仍是 Observed Session 数据的权威来源。
- `index.db` 仍是可删除重建的派生索引，不得写入权威业务状态。
- 用户没有显式授权时，不得启动、恢复、终止或 Handoff 任何 Current Run。
- Reconciliation 不得把观察结果解释为新的用户授权。
- 缺失或矛盾证据必须保持 Unknown、Waiting 或 Needs Review，不得猜测身份。
- Handoff Artifact 继续位于 Project 之外，只保存受约束的私有内容。
- Task、Snapshot 和日志不得保存 prompt、工具参数、工具输出或 Provider 会话正文。
- Managed Current Run 继续使用 ADR 0009 定义的私有 tmux 环境。

## 5. 目标架构

### 5.1 依赖方向

```text
presentation/tui
      |
      v
application commands + queries -----> domain
      |
      v
application ports
      ^
      |
adapters: sqlite / providers / tmux / process / terminal / clipboard / notification

bootstrap (main.rs) 只负责构造和连接上述对象
```

允许的依赖为：

| 模块 | 可以依赖 | 禁止依赖 |
| --- | --- | --- |
| `domain` | 标准库中的纯数据能力 | application、adapters、presentation、I/O 实现 |
| `application` | domain、由 application 拥有的 port trait | presentation、具体 Adapter、`rusqlite`、`Command`、Ratatui |
| `adapters` | domain、application ports、外部库 | presentation、Application Service 的具体实现细节 |
| `presentation` | application 的命令/查询契约、只读 View Model | Store、tmux、进程、Provider 文件、权威状态写入 |
| `main.rs` | 所有顶层模块 | 业务规则、SQL、Provider 分支、UI 工作流规则 |

`application` 中允许出现时间、ID、存储和外部行为的抽象端口，但具体系统调用必须由
Adapter 实现。只有确实存在替换边界的外部能力才建立 trait，不为每个结构体机械增加
接口。

### 5.2 目标运行流程

后台周期应显式分为四步：

```text
Collect
  读取 Provider 源、进程事实和可丢弃索引
  产出 ObservationFrame，不写权威状态

Reconcile
  使用 ObservationFrame 推进已存在的 Binding、Current Run 和 Task 状态
  所有写入通过权威 Repository 事务完成

Project
  组合 ObservationFrame 与权威状态，生成只读 Snapshot

Publish
  原子替换 ReadModelCache 中的 Snapshot
```

Collect 失败、Reconcile 失败和 Project 失败分别产生结构化 Diagnostic。不得再以一个
`RefreshService::refresh()` 同时表示扫描、业务状态迁移和发布。

### 5.3 应用命令边界

每个工作流拥有独立 Handler，例如：

```text
application/
  managed_session/
    start_new.rs
    start_resume.rs
    binding.rs
    current_run_access.rs
  handoff/
  session_metadata/
    edit.rs
    curate.rs
  observation/
  reconciliation/
  ports/
```

Handler 接受稳定身份和用户输入，返回结构化 Outcome。它不得接收 `&mut Ui`、不得拼接
界面提示语、不得写剪贴板，也不得直接发送 TUI rescan channel。

Presentation 负责：

- 把按键和表单草稿转换为命令请求。
- 把 Outcome 或错误码映射为界面文案。
- 执行纯界面副作用，例如剪贴板写入和状态提示。
- 根据 Outcome 中的 `state_changed` 请求重新投影。

### 5.4 TUI 状态边界

使用一个明确的 Overlay State 或 Overlay Stack 取代并行的十余个
`Option<Confirmation>`。每个工作流模块共同拥有自己的交互状态、输入转换和渲染：

```text
presentation/tui/
  shell/
  new_session/
  session_editor/
  session_detail/
  task_detail/
  hidden_inventory/
  guide/
```

`Ui` 只保存临时交互状态和已经加载的 UI Preference。Session Alias、Description、
Curation、Managed 状态和 Operation Task 都必须来自 Snapshot 或 Query，不得由 UI
直接加载或写入。

### 5.5 Provider 边界

保留当前按 capability 划分的 Provider Registry 思路，但 port 应由使用它的
Application 侧拥有，Claude/Codex Adapter 负责实现。新增 Provider 能力时只允许：

1. 在 port 中声明应用真正需要的能力。
2. 在 Provider Adapter 中实现能力。
3. 在 Registry 中注册实现。

不得在 Application、Refresh、TUI 和多个 Helper 中重复新增 `match Provider`。

## 6. 持久化目标

### 6.1 存储拓扑

重构后只保留以下存储角色：

| 存储 | 角色 | 内容 |
| --- | --- | --- |
| Provider source files | 外部权威来源 | Provider-native Session 记录 |
| `index.db` | 可丢弃派生索引 | 归一化 Observed Session 元数据 |
| `state.db` | Mudi 权威状态库 | Operation Task、Managed 关系、Binding Receipt、Session Metadata、Curation；未来可加入 Checkpoint |
| Handoff Artifact root | 私有内容存储 | 经校验的 Handoff Artifact 正文 |
| `profile.json` | UI Preference | 主题、布局、Guide 状态等非业务偏好 |

Task Store 继续作为 Operation Task 的逻辑权威边界，但不再要求独占一个物理 SQLite
文件。Repository 和事务边界按业务所有权划分，Schema 生命周期由同一个
`StateDatabase` 管理。

### 6.2 Schema 规则

- `state.db` 由唯一 `SchemaOwner` 创建。
- 使用 `PRAGMA user_version`，初始重构版本为 `1`。
- 启用 `foreign_keys = ON`、WAL 和明确的 `busy_timeout`。
- 当前完整 Schema 集中定义，不在各 Repository 的 `open()` 中自行建表。
- Repository 不执行 `PRAGMA table_info`、动态拼接 `ALTER TABLE` 或隐式修复 Schema。
- 跨 Task、Managed Session、Binding Receipt 和 Session Metadata 的一致性写入使用同一
  SQLite Transaction。
- Schema 合约测试直接验证表、列、约束、索引和 `user_version`。

### 6.3 一次性重置策略

本次重构不迁移或导入重构前的数据：

1. 首次切换到 `state.db` 时，将现有 `tasks.db`、`managed-launches.db`、
   `session-labels.json`、`index.db` 和 Handoff Artifact root 移入带时间戳且
   owner-only 的 `legacy-reset/` 备份目录。
2. 创建全新的 `state.db` 和 `index.db`。
3. 应用代码不读取、探测或导入备份内容。
4. 旧 Handoff Artifact 与旧 Task 引用作为同一备份保留，避免静默销毁用户可能仍需要
   的私有结果，也避免在新的活跃 Artifact root 中留下无权威引用的文件。
5. 该重置只发生一次，不保留长期 legacy 分支。

首次切换的判断依据是“尚无 `state.db`，但存在重构前的旧文件集”，不是任意版本不
匹配。完成 `state.db` v1 后，未来遇到未知 `user_version` 必须 fail fast，并要求显式
迁移或显式重置。不得静默清空未来已发布版本的权威数据。

### Phase 1：建立权威 State Database（已完成）

目标：首先消除当前真实故障来源和未来 Schema 演进风险。

工作项：

1. 在 `adapters/persistence/state/` 建立 `StateDatabase` 和集中 Schema。
2. 为 Operation Task、Managed Session、Binding、Session Metadata/Curation 建立按业务
   划分的 Repository 实现。
3. 保留现有应用服务接口，先把内部存储依赖替换为 Repository。
4. 在一次受控切换中把所有权威调用指向 `state.db`，不做双写。
5. 实施第 6.3 节的一次性备份与重置。
6. 删除旧 Store `open()` 中的 Schema 探测和零散迁移函数。

验收门槛：

- Fresh install 可创建完整 `state.db` v1。
- 模拟重构前旧文件集时执行一次性重置，不尝试逐列兼容。
- 已存在的 `state.db` 使用未知 `user_version` 时 fail fast，不自动清空。
- New、Resume、Binding、Current Run re-entry、Handoff、Task retry/delete、Session Edit
  和 Curation 的行为测试全部通过。
- 并发打开数据库、唯一约束、事务回滚、WAL 和 `busy_timeout` 有专门测试。
- `PRAGMA integrity_check` 通过。
- `index.db` 删除后可重建，删除 `state.db` 才会丢失 Mudi 权威状态。

可停止状态：即使暂不继续拆模块，当前 New 的旧 Schema 回归路径已经被彻底移除。

完成记录（2026-08-27）：`StateDatabase` 现为唯一权威 Schema Owner；Operation Task、
Managed Session、Binding、Session Metadata/Curation 已统一使用 `state.db` v1。首次切换
会把旧权威 Store、可丢弃 Index 与 Handoff Artifact root 一并移入 owner-only 的
`legacy-reset/`，再发布全新 `state.db` 与 `index.db`；失败时恢复完整旧集合。所有连接
统一启用 foreign keys、WAL、五秒 `busy_timeout` 与 owner-only 权限，未知版本在任何
持久化 PRAGMA 前 fail fast。旧 Repository 的运行时建表、Schema 探测、`ALTER TABLE`
和 JSON Label Store 兼容路径均已删除；Schema、并发初始化、事务回滚、WAL 可见性、
权限、cutover 回滚与完整工作流测试已通过。

### Phase 2：反转 Application 依赖（已完成）

目标：让 application 只表达用例和政策，不包含 UI 或具体系统实现。

工作项：

- 把 Repository、Clock、ID、Provider Runtime、Process Evidence、tmux、Terminal、
  Notification 等 port 放到 application 所有的边界模块。
- 将 SQLite、tmux、进程检查、Terminal.app、AppleScript、Clipboard 和通知实现移动到
  `adapters/`。
- 将 `ApplicationController::handle` 拆成工作流 Handler；Composition Root 只做路由和
  wiring。
- Handler 返回 typed Outcome 和 typed Error；Presentation 负责文案。
- Application 不再接收 `Ui`、Clipboard 或 rescan channel。

验收门槛：

- `src/application/` 对 `crate::presentation` 的依赖数量为 0。
- `src/application/` 不再直接使用 `rusqlite::Connection` 或
  `std::process::Command`。
- macOS/tmux 不可用时，应用用例测试可通过 fake port 完整执行。
- 授权、身份校验和失败安全测试保持原语义。

可停止状态：功能行为不变，但每个用例可以独立测试和替换 Adapter。

完成记录（2026-08-27）：Repository、Clock、ID、Provider Runtime、进程证据、Managed
Launch、Current Run、Terminal、通知与 Clipboard 边界已经反转；SQLite、Provider、
进程、tmux、Terminal.app、通知、Handoff Worker、Observation、Refresh 与 Successor 的

Workflow Handler 接收稳定身份和 typed input，并返回 typed outcome/error；
`presentation/tui/router.rs` 负责界面文案、Clipboard 与重新投影请求，`main.rs` 只负责
composition。Application 不再依赖 Presentation、具体 Adapter、`rusqlite` 或
`std::process::Command`，Presentation 不再依赖 Adapter；fake-port Handler 测试覆盖授权、
目标消失、非法状态、写入失败、typed outcome 与权威状态是否改变。完整 Rust 格式化、
Clippy、单元/集成测试、production render、Managed Binding 与依赖边界检查均已通过。

### Phase 3：拆分 Observation 与 Reconciliation（已完成）

目标：消除 Refresh 作为隐藏写入中心的问题。

工作项：

- Collector 产出不可变 `ObservationFrame`。
- Binding、Managed Current Run、Resume eligibility 和 Task 状态推进进入明确的
  Reconciliation Service。
- Session Metadata 与 Managed Metadata 不再通过定时 Refresh 双向同步；应用命令或
  Reconciliation 在同一权威状态 Transaction 内写入最终状态。
- Snapshot Query 只组合 ObservationFrame 与 Repository 读取结果。
- 后台 Poller 按 Collect -> Reconcile -> Project -> Publish 调用，并分别记录诊断。

验收门槛：

- Collect 和 Project 测试运行时以只读 Repository 即可完成。
- 对权威 Repository 记录调用后，Collect 和 Project 的写入次数为 0。
- Reconciliation 在没有已授权 Registration/Task 时不能创建任何控制关系。
- 同一 ObservationFrame 重放具有幂等结果。
- 进程证据不确定时仍保持 Unknown、Waiting 或 Needs Review。

可停止状态：后台周期仍可保持两秒一次，但其每一步的权限和失败语义已经清晰。

完成记录（2026-08-27）：旧 `RefreshService::refresh()` 已删除；TUI-owned
`RefreshCycle` 只按 Collect -> Reconcile -> Project -> Publish 排序调用四个独立服务。
Collect 产出只含规范化元数据和一次批量进程证据采样的不可变 `ObservationFrame`，只依赖
只读 `ManagedObservationQuery`；Reconciliation 只推进 Frame 中已有权威 Registration 的
Binding，并在同一阶段对已有 Operation Task 做恢复对账，缺少授权记录时保持无写入。
Project 仅通过只读 `ManagedProjectionQuery` 与 `OperationTaskQuery` 组合 Frame、Managed
provenance、Registration 和 Task 读模型；Publish 在完整 Snapshot 产生后原子替换缓存。
诊断携带 Collect、Reconcile、Project 或 Publish 阶段身份。

Managed Launch Title 与身份关联现在在一个 `state.db` Transaction 中提交，Binding 建立
Managed Session 时也在同一权威 Transaction 写入最终 Description；定时双 Store Metadata
同步及其 Repository API 已删除。重放同一 Frame、无授权对账、模糊进程证据、重启
Binding、Title/Metadata 幂等、只读端口调用、部分阶段失败、原子发布，以及 Provider 源的
append、truncate、delete、malformed 与 Index rebuild 均有回归测试。TUI 明确拥有、终止并
观察后台 task；两秒轮询和显式 rescan wakeup 保持不变。

### Phase 4：按职责拆解 Managed Session

目标：在稳定端口之上拆掉 `managed_sessions.rs` 的多层混合，而不改变行为。

建议拆分：

```text
domain/
  managed_session.rs
  managed_current_run.rs
  binding.rs

application/managed_session/
  start_new.rs
  start_resume.rs
  binding.rs
  current_run_access.rs
  reconciliation.rs

adapters/persistence/state/
  managed_sessions.rs
  bindings.rs

adapters/system/
  process.rs
  tmux.rs
  terminal_macos.rs
```

拆分顺序按现有工作流逐条迁移：New -> Binding -> Current Run Access -> Resume -> Recovery。
每迁移一条工作流，就删除旧模块中的对应实现，不建立永久 facade 或双实现。

验收门槛：

- Domain 类型不引用 Config、SQLite、Provider Registry 或系统路径。
- Application 工作流只通过 port 访问 Repository 和系统能力。
- tmux 命令构建和 AppleScript 只存在于 Adapter。
- 不再存在同时拥有领域状态机、SQL 和系统命令的生产模块。

可停止状态：任意完成的工作流都已拥有清晰边界，未迁移工作流仍可继续工作。

完成记录（2026-08-27）：Provider-neutral Managed Launch、Managed Session、Managed Current
Run 与 Binding Receipt 已迁入 `domain/`；Provider 启动命令只在 application port 与 launch
adapter 之间传递，不再进入领域记录或权威持久化。Managed New、Binding、Current Run
Access、Resume 与 Recovery/Reconciliation 分别由独立 application 模块拥有，旧
`application/managed_sessions.rs` 已删除。

Managed SQLite Repository 与 Binding 原子发布事务现归于
`adapters/persistence/state/`；Provider evidence、进程身份、tmux 和 Terminal.app 实现按
adapter 职责拆分。Native Session ID、PID-start 复验、Needs Review、显式授权、私有 tmux
和不自动重试语义保持不变；Managed New、Binding、Launch Recovery、Current Run Access、
Resume 与 Restart 集成套件共 74 个测试通过。

### Phase 5：收敛 TUI 工作流状态（已完成）

目标：让新增交互不再扩大一个全局 `Ui` 和一个全局按键函数。

工作项：

- 引入明确的 `OverlayState`/`OverlayStack`，替换并行 Modal `Option`。
- New、Edit、Handoff Confirmation、Task Confirmation、Hidden Inventory 和 Guide 分别迁入
  独立交互模块。
- Session Metadata/Curation 全部通过应用命令修改。
- Snapshot 已包含渲染所需的 Title、Description、Curation 和可用操作，不让 UI 自己
  再次推导业务资格。
- 分离交互状态测试和 Ratatui render fixture 测试。

验收门槛：

- `Ui` 不持有 `SessionLabels` 或任何 Repository。
- 一个输入事件只有一个明确的交互所有者。
- Overlay 的输入优先级与绘制层级由同一个状态结构决定。
- TUI 只能发出命令或纯界面动作，不能直接写业务数据。
- 现有键盘流程、最小终端尺寸和 production render 测试保持通过。

可停止状态：TUI 仍是同一产品界面，但后续工作流可作为独立模块加入。

完成记录（2026-08-28）：Session Metadata/Curation 的 Alias、Description、Hide、Restore
与永久排除仍由 typed application Handler 和权威 Repository 执行；Project bulk Hide 只
持久化确认时的稳定 Session 身份快照。Projection 现在把 resolved Title、Description、
Curation disposition、Hidden Inventory membership 与 action eligibility 一并发布到
`RefreshSnapshot`，Open Hide 限制和 validated Open override 归 application read model
所有。Presentation 不再持有、打开或 reload `SessionLabels`、Repository 或权威状态路径。

TUI 现在只有一个 `OverlayState` 字段决定 input priority 与 drawing order。New、Directory
Browser、Session Edit、Detail、Guide、Hidden Inventory、Handoff、Managed Resume 和 Task
confirmations 都持有自己的 transient state 与 input conversion；Confirmation、Guide、
Session Edit 和 Hidden Inventory 用显式 underlay 恢复来源。Esc、确认、validation failure、
nested directory selection 与 target disappearance 都有明确状态转换。现有键位、文案、
响应式布局和 production render fixtures 保持不变；application read-model/command 测试与
独立 interaction state-machine 测试覆盖 identity isolation、bulk snapshot、degraded state、
唯一 input owner、focus restoration 和稳定 target identity。

### Phase 6：Checkpoint 实现准入

只有以下条件全部满足，Checkpoint 才能进入 PRD 后的 implementation ticket：

- Phase 1 至 Phase 3 的门槛全部通过。
- Checkpoint durable representation 和 retention 已确定。
- 最小 repository evidence Schema 已确定，并通过隐私审查。
- User-authored、Agent-proposed 和 mechanically observed 字段权限已确定。
- Checkpoint 与 Resume/Handoff 的交互已确定，且不暗示自动授权。
- Checkpoint 的聚合边界和 Repository 事务边界已确定。
- PRD Acceptance Criteria 可以在不读取会话正文的情况下验证。

Checkpoint 应作为第一个验证新架构的完整垂直切片，而不是再加入
`managed_sessions.rs`、`refresh.rs`、`UiAction` 和 `Ui` 的新分支。

## 8. 测试策略

### 8.1 Schema 合约测试

- 从空目录创建数据库，验证完整 v1 Schema，而不是由当前 Store 间接建库。
- 验证 `user_version`、表、列、约束、外键和索引的精确集合。
- 验证旧文件集的一次性 reset，以及未知 `state.db` 版本的 fail-fast 行为。
- 不再把“当前 Schema 加几个旧字段”称作 legacy migration 测试。

### 8.2 Repository 合约测试

同一组测试运行在 SQLite Repository 实现上，覆盖：

- 原子写入与回滚。
- 幂等 Reconciliation。
- 唯一身份和非终态 Task 约束。
- 多进程打开、busy timeout 和 WAL 可见性。
- Metadata、Binding、Managed Session 和 Current Run 的一致性。

### 8.3 Application 测试

- 使用 fake ports 验证授权和状态转换，不启动 tmux、Terminal 或真实 Provider。
- 每个 Handler 独立验证输入、Outcome、错误和请求的外部能力。
- 对失败安全规则使用表驱动测试，避免只从 TUI 端到端覆盖。

### 8.4 Adapter 测试

- Provider 解析和进程证据继续使用真实格式 fixture。
- tmux、Terminal、Clipboard 和 Notification 测试只验证命令边界与退出状态。
- 对不可用、超时、PID 复用、矛盾证据和部分 I/O 失败保留专门测试。

### 8.5 Presentation 测试

- 交互状态机测试验证输入所有权和发出的命令。
- Render fixture 只验证布局和可见语义，不承担业务状态机证明。
- 端到端 UI 测试保留少量关键主路径，不再复制每个 Handler 的全部组合。

## 9. 架构门禁

CI 通过 `python3 scripts/check_architecture.py` 运行无第三方依赖的轻量门禁，防止边界在
后续需求中重新退化：

- `ARCH001`：Domain 不引用 Application、Adapters、Presentation、SQLite、进程命令、
  Ratatui 或 filesystem/network 实现。
- `ARCH002`：Application 不引用 Presentation、具体 Adapter、SQLite、Ratatui 或直接
  `std::process::Command` 构造。
- `ARCH003`：Presentation 不引用权威 Repository、`StateDatabase`、Provider source
  reader、进程 probe、SQLite、权威状态路径或具体系统 Adapter。
- `ARCH004`：`src/adapters/persistence/state/mod.rs` 是唯一权威 State Schema Owner，
  同时拥有 `StateDatabase`、Schema 创建和 `user_version`。
- `ARCH005`：State Schema Owner 以外的权威 Repository 不使用 `PRAGMA table_info` 或
  `ALTER TABLE` 进行普通 open-time migration。
- `ARCH006`：Observation Collect 与 Project 不引用权威写 Repository 或调用其写接口。
- `ARCH007`：SQLite、进程命令、tmux、Terminal.app、Notification、Clipboard 与 Provider
  进程的具体实现只位于 `src/adapters/`，其中包括 detached Worker Adapter。

契约测试为每条规则构造至少一组允许与禁止的临时源码树，并验证失败包含规则 ID、文件和
行号。扫描只排除 `src/**/tests/`、`src/**/fixtures/` 与 `*_test.rs`；内联测试仍受检查。
`src/adapters/persistence/index/` 仅从权威 Schema/迁移规则中排除，因为它是可丢弃索引。
macOS CI 在完整 `cargo test` 前依次运行 fixture 契约与真实仓库检查。

## 10. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 一次性状态重置导致数据丢失 | 重置前移动到 owner-only 时间戳备份；运行时不读取备份 |
| 合并到 `state.db` 后多进程争用 | WAL、busy timeout、短事务、并发 Repository 合约测试 |
| Detached Handoff Worker 与 TUI Schema 不一致 | Worker 和 TUI 只通过同一个 SchemaOwner 打开同一个版本 |
| 重构期间行为漂移 | 每次只迁移一条工作流，先保持现有行为测试，再删除旧实现 |
| 抽象数量失控 | port 只对应真实外部边界；不为纯计算或单实现数据结构建立 trait |
| Refresh 拆分后周期变慢 | 对 Collect、Reconcile、Project 分别计时；保持增量索引和批量证据采样 |
| Checkpoint 压力打断基础重构 | Phase 6 准入门槛写入实施票据，不接受提前 Schema 或 UI 分支 |
| 回滚时新旧状态分叉 | 切换不双写；回滚需明确丢弃新 `state.db` 并恢复整套备份 |

## 11. 实施纪律

- 每个 PR 只完成一个 Phase 中的一个可验证工作项。
- 纯移动文件与行为修改不得混在同一个 Commit 中。
- 迁移到新实现后立即删除旧实现，不留下无限期兼容 facade。
- 不在重构 PR 中顺便改变产品文案、键位、视觉设计或版本范围。
- 每个 PR 描述必须写明修改的依赖方向、权威数据边界和失败语义。
- 更新模块职责后同步更新 `docs/source-map.md`。
- 如果实施发现计划与现有 ADR 冲突，先停止并更新 ADR，不通过代码绕过。

## 12. 整体完成定义

本次架构重构完成时，应满足：

1. Mudi 权威状态由一个版本化 `state.db` 管理，派生索引仍可独立删除重建。
2. Application 不依赖 Presentation 或具体系统 Adapter。
3. Observation、Reconciliation、Projection 和 Publication 是可独立测试的阶段。
4. Managed Session 的领域、用例、持久化和系统实现分别位于明确边界。
5. TUI 不写权威业务状态，Overlay 输入所有权唯一。
6. 当前 New、Resume、Binding、Current Run、Handoff、Task、Metadata 和 Curation 行为
   全部保持可用。
7. 架构门禁和测试可以阻止旧 Schema 回归及跨层依赖重新出现。
8. Checkpoint 可以作为一个新的垂直切片进入实现，而不需要扩大现有全局编排中心。
