Session Core promoted to [`v2.0.0`](../../../feature/v2.0.0/README.md) and Work Continuity

they satisfy the repository's ADR process.

The detailed Work Continuity discussion lives in
[`docs/feature/v2.0.1/work-continuity/discussion.md`](../../feature/v2.0.1/work-continuity/discussion.md).
It does not change version scope or replace a future GitHub Issue PRD.

## Status after v2.0.0 and v2.0.1

`v2.0.0` is the first deliverable increment of Mudi 2.0. It fixes Managed Session
Core as the shared, dual-Provider foundation: private tmux, conclusive identity binding,
external-terminal access, precise resume, and restart reconciliation. `v2.0.1` adds
developer-directed Work Continuity without introducing an Action Runtime or Flow Scheduler.
Their scopes are authoritative in `feature/`, not in this exploration record.

The agreed discussion order after these two versions is Bounded Action Runtime (`v2.1.0`),
Verified Action Results (`v2.2.0`), then Approved Flow Scheduler (`v2.3.0`). These are
roadmap directions only: each needs its own requirements discussion, feature scope record,
and GitHub Issue PRD before implementation.

The later sections headed **Candidate concrete product slice**, **Workflow layer after the
core**, and **Embedded managed terminal hypothesis** preserve historical exploration. They
are not v2.0.0 or v2.0.1 requirements. In particular, the historical Codex-first
suggestion is superseded: v2.0.0's Managed Session Core must support both Codex CLI and
Claude Code, and embedded terminal rendering remains deferred.

## Starting observation

Mudi v1 is primarily a local observation surface for Claude Code and Codex CLI
Sessions, with explicitly authorized Handoff as its first control capability. The current
Project area is at risk of mixing several responsibilities:

- current Project, Worktree, and Open Session navigation;
- historical Session browsing;
- selected Session metadata;
- an empty conversation workspace that the current product boundary cannot populate.

At the supported `80x24` terminal size, this composition leaves only two content rows in
the Session Tree despite multiple Open Sessions. That exposes a product problem rather
than only a responsive-layout problem: the core Project surface no longer has one clear
job.

## User-stated problem

The developer's problem is broader than terminal persistence:

- one Session terminal is a narrow place to operate one Agent and cannot coordinate many
  concurrent bodies of work;
- multiple Projects require multiple Session terminals, making global state and control
  fragmented;
- independent Sessions have no reliable way to exchange work or participate in one
  coordinated execution;
- the developer needs one place to supervise, route, and intervene across all of them.

Private tmux is proposed because it gives Mudi durable, addressable execution
containers that it can launch and control. Rendering the tmux terminal inside Mudi
is an optional interaction surface. Opening a separate terminal and attaching to the same
managed tmux Session may provide the same direct developer access without defining the
control plane itself.

## Control-plane interpretation

The user describes Mudi as the central control hub rather than a peer Agent. A
candidate separation of responsibilities is:

```text
Developer                         final authority and direct intervention
    |
Mudi control plane         registry, routing, policy, scheduling, evidence
    |
private tmux execution fabric     durable and addressable terminal processes
    |
Provider Sessions                 workers that reason and perform coding work
```

Sessions do not directly control one another. A Session may request delegation, send a
message, or publish a Result through Mudi. The control plane records the source and
target, checks current state and authority, performs the delivery, and observes the
outcome. tmux can transport terminal input, but it does not define the meaning or authority
of that input.

This makes embedded terminal rendering, an external `tmux attach`, and future client
surfaces alternative views over the same control plane. None of them owns the managed
execution state.

### Flow-aware delegation

The developer expects Mudi to know the active Flow before Session A needs Session
B. In the candidate language above, the Flow should not become a separate synonym: an
Execution Plan defines the allowed steps and transitions, and a Workflow Run is one active
execution of that plan.

```text
Execution Plan
  Step A: implementation
    on ready_for_review -> Step B
  Step B: review in a distinct Session

Workflow Run
  Session A publishes ready_for_review
  -> Mudi validates the Result and transition
  -> Mudi selects or launches Session B
  -> Mudi delivers the declared review input
```

Session A does not authorize or directly launch Session B. It reports a Result, condition,
or permitted delegation request. Mudi already knows whether B belongs to the active
plan, whether the transition is currently valid, and which constraints apply. A request
outside the known plan is a proposed plan change rather than an executable instruction.

### Points accepted in the discussion

These are points explicitly accepted during the exploration, but they are not yet a 2.0
PRD or architectural decision:

- Session-to-Session communication and delegation pass through Mudi.
- Mudi may execute an already-declared Flow transition without asking for a new
  confirmation at that transition.
- A Session may propose a Step that is absent from the active Execution Plan.
- The proposal creates a Plan Revision; it does not immediately create executable work.
- Mudi pauses the affected path until the developer explicitly approves the Plan
  Revision.
- A managed Session receives a user-facing Title and Description so the developer can
  distinguish many Sessions within one Project; the tmux presentation may mirror them.
- Title and Description belong to the provider-native Session and survive precise resume
  across its Current Runs. A Handoff creates a distinct Successor Session with its own
  independently assigned Title and Description.
- Spec synthesis and Ticket decomposition remain Agent work provided by existing Skills
  such as `to-spec` and `to-tickets`. Mudi orchestrates those actions and records
  their result references; it does not define or interpret the artifacts' authoring
  semantics.
- For a Skill-backed Action, Mudi explicitly knows the Skill name, input references,
  target Session, and expected result type. The provider Session owns Skill execution and
  content semantics.
- Approving and publishing the `to-tickets` breakdown does not authorize code execution.
  The developer separately invokes `Start Flow` to authorize the declared plan. After that
  one authorization, Mudi may advance declared transitions automatically; a Plan
  Revision or authority expansion still requires explicit approval.
- Mudi attaches a structured Result Contract when it dispatches a Skill-backed
  Action. For an Action-bounded non-interactive Current Run, the Action Worker captures the
  Provider's final structured output and process exit, validates the payload and external
  evidence, and constructs the Result. MCP is a fallback to reconsider only if this channel
  proves insufficient.
- The required managed execution substrate must support both Codex and Claude Code.
  Mudi therefore must not make Codex app-server its central or required control
  path. Private tmux is the common execution fabric; app-server may only add optional
  Codex-specific capabilities.
- A normal TUI exit pauses automatic Flow advancement but does not terminate managed tmux
  Sessions. An Action already Running may reach and persist its Result boundary, but no
  dependent Action starts until the developer reopens Mudi and explicitly resumes
  the Flow. Immediate interruption remains a separate `Stop Flow` operation.
- A daemon is an optional runtime host for callback reception, reconciliation, and
  scheduling, not a product-domain requirement. Whether those responsibilities run in the
  TUI, a detached Worker, or a daemon must not change Flow semantics: a Paused Flow never
  dispatches a dependent Action.
- Each managed Current Run has exactly one Input Owner. Read-only viewing does not transfer
  ownership. `Take Control` makes it Developer-owned and pauses only the affected Flow
  path; `Return to Flow` revalidates state before restoring Automation ownership. tmux
  detach alone never returns ownership.
- Each Automation-owned Action starts a fresh non-interactive Current Run that precisely
  resumes the assigned provider-native Session inside its managed tmux workspace. The
  Provider process exits at the Action boundary; later Actions and developer intervention
  create new Current Runs without creating a new Session.

### Proposed end-to-end journey

The user proposes that one Agent creates the initial Flow through an interactive planning
journey inside Mudi:

```text
select Project
  -> Start Codex
  -> enter a name and description
  -> Planning Session grills the developer about the requirement
  -> Agent records relevant ADRs and invokes to-spec
  -> Agent invokes to-tickets
  -> Mudi receives the published Ticket references and dependency edges
  -> Mudi creates the known Flow from the approved outputs
  -> execute Tickets in sequence through managed Sessions
```

The Planning Session is a normal provider-native Session running in the managed environment,
not a planning algorithm implemented by Mudi. Mudi supplies the Project
context, interaction surface, artifact workflow, approvals, and the transition into
execution.

The Title and Description belong to the managed Session for user recognition, not to a
separate Initiative invented by Mudi. The Title is the compact name shown in lists
and tmux presentation; the Description explains why the Session was started. Neither is a
stable technical identity, and Mudi control must continue to use internal and
provider-native IDs.

The semantics and publishing workflow of Spec and Tickets belong to the Agent Skills, not
to Mudi's domain model. In the currently installed workflow, `to-spec` synthesizes
the conversation into a Spec/PRD and publishes it to the configured issue tracker;
`to-tickets` turns a Spec, plan, or conversation into tracer-bullet Tickets with blocking
edges. Mudi only needs the execution-facing contract: which Session should perform
the Action, which inputs it receives, whether it completed, and which published references
or dependency edges it returned.

A candidate Skill-backed Action therefore looks conceptually like:

```text
Action
  id: <Action ID>
  type: invoke_skill
  skill: to-spec
  target: Planning Session
  inputs: current conversation and Project context
  result contract: published Spec Issue reference
```

This is control metadata, not a reimplementation of the Skill. Other Action types could
later cover executing a Ticket, requesting developer input, or producing a Handoff.

The Action dispatch and final output form the accepted primary control loop:

```text
Mudi -> Action ID + Skill + inputs + Result Contract -> Action Worker
Mudi <- process outcome + final structured output    <- Provider Current Run
```

The Worker already owns the Action and Provider process identities, so the Agent does not
need to echo an Action ID or authenticate a separate callback. A successful process exit
is necessary but not sufficient: the final payload must satisfy the Action-specific JSON
Schema, and Mudi must independently validate referenced artifacts before persisting
the Result and making it available to a dependent Action. Terminal prose outside the
structured final output has no completion authority.

If final structured output later proves inadequate, one fallback candidate is a
Mudi MCP bridge:

```text
Codex or Claude Agent
  -> calls mudi.complete_action(outcome, output)
  -> Provider's MCP client
  -> mudi mcp-bridge over stdio
  -> authenticated local socket
  -> Mudi coordinator and Action Store
```

This is deliberately deferred. It adds Provider MCP configuration, capability binding,
dynamic validation, and a durable callback endpoint. A `mudi action complete`
shell command could expose the same fallback bridge. Neither is required for the accepted
first implementation.

### Technical feasibility of structured Action Results

This control loop is technically feasible with the currently installed `codex-cli 0.146.1`.
Three integration levels have been evaluated:

1. **Detached Action Worker.** Both `codex exec` and `codex exec resume` accept
   `--output-schema <FILE>` to constrain the final assistant response and `--json` to emit
   lifecycle events as JSONL. Mudi can create an Action record, generate the
   Action-specific JSON Schema, precisely resume the target native Session, invoke the
   selected Skill, capture the structured final response, validate it again, and commit
   the Result to its authoritative store.
2. **Codex app-server client.** The generated protocol for the installed version exposes
   `skills/list`, a structured `skill` user-input item, `thread/resume`, `turn/start`, an
   `outputSchema` field on each Turn, and `turn/completed` lifecycle evidence. This can
   drive a persistent interactive Session without terminal-screen parsing and can route
   Codex approval and developer-input requests back through Mudi.
3. **Provider-neutral managed terminal.** Mudi can run either Codex or Claude Code
   as one non-interactive, precisely resumed Current Run in a private tmux workspace,
   dispatch a Provider-specific Skill invocation together with an Action-owned Result
   Contract, and capture its final structured output. The validated Result and Provider
   process boundary, rather than terminal text, close the provider-neutral control loop.

The locally installed Provider CLIs expose the required primitives. Codex CLI `0.146.1`
can configure stdio or HTTP MCP servers and accepts JSON Schema for `exec` results. Claude
Code `2.1.207` accepts `--mcp-config` and `--strict-mcp-config`, and its non-interactive mode
also accepts `--json-schema`. These facts establish feasibility for the installed versions,
not a permanent cross-version compatibility guarantee.

The existing Handoff implementation already proves much of the first path. Its detached
Worker precisely resumes a native Codex Session, invokes the managed
`mudi-handoff` Skill, captures the provider output, validates its declared Artifact
contract, and updates an authoritative Operation Task Store. General Action execution
would replace the fixed Handoff prompt and Markdown validator with a declared Skill,
inputs, and JSON Result Contract.

The paths have different risk. The detached Worker extends a repository-owned and tested
boundary but does not provide a continuously interactive client protocol. The tmux path is
portable across Provider CLIs but requires explicit input ownership and conclusive binding
among pane process, native Session, Action, final output, and Result. Action-bounded Runs
remove provider-screen Idle detection but make concurrent-resume prevention a hard
invariant. app-server gives Mudi native
Thread, Turn, Item, Skill, approval, and completion events, but its top-level CLI surface
remains marked experimental and is Codex-specific. Using it optionally would require a
versioned adapter, generated protocol fixtures, reconnect handling, and behavior consistent
with the common tmux control contract.

Structured shape alone also does not prove semantic success. Mudi must still
validate referenced Issues, Tickets, revisions, checks, or Artifacts before advancing a
dependent Action. It must also prevent concurrent Current Runs from writing to the same
native Session and preserve the existing rule that an uncertain interrupted attempt is
never retried automatically.

### Action-bounded Current Runs

Automation does not keep one interactive Provider TUI open and inject every Action into
it. Instead, each Action starts a new non-interactive Current Run that precisely resumes
the same provider-native Session:

```text
managed Session A
  +-- Current Run 1  non-interactive to-spec Action
  +-- Current Run 2  non-interactive to-tickets Action
  +-- Current Run 3  interactive developer intervention
  `-- Current Run 4  non-interactive Ticket Action
```

Only one Current Run may be Open for the Session. An Automation-owned Run receives the
declared Skill, inputs, permissions, and Result Contract at process start, then exits at
the Action boundary. `Take Control` instead starts or resumes an interactive Current Run;
after the developer exits it, the Session remains Developer-owned until an explicit
`Return to Flow` revalidation.

This model preserves native conversation continuity while creating a conclusive process
boundary for each Action. It avoids guessing whether a long-running Provider TUI is Idle,
waiting for approval, or still producing output. tmux remains the durable workspace,
process surface, and place where the developer can inspect the latest Run or take direct
control.

### TUI exit and Flow pause

The TUI, Flow, and managed Session have independent lifetimes. On a normal exit,
Mudi first persists the Workflow Run as Paused and then closes the interface:

```text
close TUI
  -> persist Flow as Paused
  -> stop dispatching new Actions
  -> allow an already Running Action to publish its terminal Result
  -> retain managed tmux Sessions
  -> require explicit Resume Flow after the TUI is reopened
```

This does not conflict with ADR 0003. The current Action may still finish in its detached
execution boundary after the TUI exits; only the scheduler transition to a dependent
Action is withheld. A per-Action Worker or durable private result inbox may therefore be
enough for this lifecycle without a permanently scheduling daemon. `Stop Flow` remains a
separate explicit control operation because interrupting a Provider midway can leave an
uncertain outcome.

A daemon can still be introduced without changing this lifecycle. It may keep MCP callback
endpoints available, reconcile tmux and Provider processes, and project persisted state for
clients. Its scheduler must consult the durable Flow state before every dispatch and do
nothing while the Flow is Paused. The main product path should depend on that execution
interface and persisted state, not on whether its current host is the TUI, a detached
Worker, or a daemon.

Unexpected TUI loss behaves differently according to the runtime topology. Without a
daemon scheduler, loss of the TUI also removes the only scheduler, so no dependent Action
can start; on restart, Mudi must reconcile the stale Running Flow to Paused before
offering Resume. Only when a daemon continues to host scheduling does Mudi need a
TUI heartbeat or control lease to prevent that daemon from advancing after an unclean UI
loss. The lease is therefore a daemon-specific mechanism, not a prerequisite for the first
version's main Flow.

## Emerging product direction

The interesting extension is not a larger usage dashboard. Mudi could become a
local control plane for coding-agent work:

```text
define work -> plan execution -> start Session -> observe and intervene
            -> validate result -> hand off or advance -> recover or retry
```

Observation remains useful, but as evidence for control and recovery rather than the
entire product. Mudi would not implement an Agent runtime. Claude Code and Codex
would continue to own inference, context, tool execution, and provider-native Sessions.

## Candidate concrete product slice

One candidate way to make the direction implementable is to treat 2.0 first as a local,
Project-scoped Session workspace, then add workflow automation only after managed Session
control and Result evidence are reliable.

### Session workspace core

1. Discover every supported Session, including Current Runs started outside Mudi.
2. Resolve Sessions into Projects and Worktrees without guessing their goals.
3. Distinguish external Current Runs from Runs launched in a Mudi-owned private
   tmux environment.
4. Start a new Codex Session or a precise resumed Current Run inside that environment.
5. Let the developer attach to a selected managed terminal. An embedded workspace and an
   external `tmux attach` flow are alternative interaction surfaces.
6. Keep managed Sessions alive after the Mudi TUI exits and reconcile their exact
   process and native Session identity after restart.
7. Offer actions according to available evidence: inspect all Sessions, but only control a
   Current Run when Mudi has the required provenance and authorization.
8. Handoff an external or managed Session to a distinct managed Successor Session and keep
   the verified lineage visible.

The managed interactive runtime may be Codex-first. Existing passive observation can
continue to cover Claude Code while provider-specific managed-control capabilities remain
explicit instead of pretending both Providers expose identical protocols.

### Workflow layer after the core

Once the Session workspace can reliably launch, observe, interact with, hand off, and
recover a managed Session, a later layer may add:

- authorized Execution Plans derived from PRDs and relevant ADRs;
- structured Steps and dependencies;
- machine-verifiable Results;
- automatic successor launch or next-Step advancement;
- pause, retry, review, and developer-input gates.

The workflow layer must consume explicit Result evidence. It must not infer completion by
scraping the embedded terminal or interpreting the last Agent message.

### Explicit non-goals of this slice

- implementing a model or Agent tool loop;
- becoming an issue tracker or the authority for product requirements;
- merging source and Successor Sessions into one identity;
- silently taking over an externally started live terminal;
- treating tmux screen text as a reliable workflow-completion protocol;
- making generic multi-Provider orchestration claims before each Provider's control
  capability is proven.

## Boundary hypothesis under discussion

### What defines the work

The developer and an Agent collaborate to produce the authoritative product and
architecture documents:

- a PRD defines the desired outcome, constraints, and acceptance criteria;
- relevant ADRs record durable architectural decisions and trade-offs.

Mudi should not create a second issue tracker or silently become the authority for
product scope. In this repository, GitHub Issues remain the issue and PRD surface.

### What controls the execution

Mudi controls how the documented work is attempted:

- generate and present an execution plan for authorization;
- select a Project, Worktree, Provider, model, and permission policy;
- start, resume, interrupt, and hand off Sessions;
- track dependencies among execution steps;
- receive approvals and requests for developer input;
- validate declared results before advancing dependent work;
- preserve execution evidence and reconcile after process or TUI loss.

### What performs the work

The Provider runtime performs reasoning and code changes. A Session is a distinct
provider-native worker. A resumed Current Run is another invocation of the same worker;
a Successor Session is a different worker even when it continues the same work.

## Work continuity and worker identity

A working interpretation offered during the discussion is:

> From the work's perspective, a Handoff is continuity. From the worker's perspective,
> the Successor is distinct.

Session A and Session B must therefore never be merged. Their relationship and evidence
remain visible, while a separate execution object preserves the continuity of the work:

```text
same documented objective
  |
  +-- Session A -- result / handoff --+
  |                                   |
  +-- Session B <---------------------+-- continues the work
```

The durable work state must not be inferred from Session lifecycle alone. An Exited
Session does not prove that the work completed, and a Busy Session does not prove that the
work is progressing correctly. This interpretation is not yet a confirmed domain rule.

## Candidate execution model

The following language is deliberately provisional:

| Candidate | Current meaning | Status |
|---|---|---|
| Execution Plan | A reviewable set of steps, dependencies, permissions, inputs, and result checks derived from the specification | Proposed |
| Plan Revision | A proposed change to an Execution Plan that becomes executable only after explicit developer approval | Accepted in discussion; not formalized |
| Workflow Run | One authorized execution of an Execution Plan | Proposed |
| Step | One declared unit in an Execution Plan | Proposed |
| Action | A declared operation that Mudi asks a target Session to perform, with known inputs and an expected result type; a Skill invocation is one Action type | Accepted in discussion; not formalized |
| Input Ownership | Exclusive authority to send input to one managed Current Run; either Automation-owned or Developer-owned | Accepted in discussion; not formalized |
| Assignment | The relationship in which one Session attempts one Step or continuing body of work | Proposed |
| Step Result | A structured result submitted by a Session and validated before dependants advance | Proposed |
| Managed Session Description | User-owned metadata explaining why one managed Session was started | Accepted in discussion; not formalized |
| Work Item | An internal unit describing what should be done | Challenged; likely duplicates the external issue/PRD authority |
| Workstream | A long-lived line of related work spanning Sessions | Challenged; too vague and easily mistaken for an Agent identity |

One possible relationship is:

```text
Project
  +-- Worktree
  +-- Execution Plan (references external Spec, ADRs, and Tickets)
       +-- Workflow Run
            +-- Step
                 +-- Assignment
                      +-- Session
                           +-- Current Run
```

This is not yet the domain model. In particular, it is not decided whether Assignment is
a necessary first-class object or whether a Step directly references one or more Sessions.

## Result contract hypothesis

The scheduler must not decide that work completed by interpreting the final paragraph of
an Agent response. A result needs declared, machine-checkable evidence. A candidate Step
Result contains:

```text
Outcome: succeeded | blocked | failed | needs_input
Worktree: <canonical identity>
Base revision: <revision>
Result revision: <revision, when applicable>
Changed files: <declared paths>
Checks: <command and observed outcome>
Artifacts: <validated references>
Summary: <human-readable result>
Next-step inputs: <structured references>
```

The exact contract depends on the Step. A planning Step, implementation Step, review Step,
and investigation Step should not be forced to publish identical code-oriented evidence.

## Project's role in 2.0

Project remains the repository-scale identity already defined in `CONTEXT.md`. It becomes
more important than a display grouping: it is the local scope in which Worktrees,
specifications, execution policy, and Sessions are resolved.

At the global level, Mudi can present Projects and the execution requiring
attention:

```text
+ PROJECTS ----------------------------------------------------------------+
| mudi       2 Open Sessions   recovery workflow running            |
| flutter-template  1 Open Session    developer input required             |
| personal-site     no Open Sessions  no current execution                 |
+--------------------------------------------------------------------------+
```

After entering a Project, the primary surface shows work execution and its worker lineage
rather than an isolated metric dashboard:

```text
PROJECT mudi
  +-- recovery execution
  |    +-- Session A  handed off
  |    `-- Session B  current worker
  +-- result-contract execution  blocked by recovery
  +-- Worktrees
  `-- unassigned Sessions
```

A Session started outside Mudi may be resolved to a Project by its working
directory without being assigned to any managed execution. Mudi must not invent its
goal from timing, directory, or transcript guesses.

## Externally started Sessions

The 2.0 scope must explicitly consider Codex Sessions that the developer starts in another
terminal, IDE, or Codex client. Excluding them would abandon Mudi's existing ability
to discover provider-native Sessions and would create a closed manager that sees only its
own work.

The unresolved distinction may belong to Current Run rather than Session:

```text
Codex Session 123
  +-- Current Run A  started outside Mudi
  `-- Current Run B  later resumed by Mudi
```

The native Session identity remains the same across both Runs. What changes is the launch
provenance, available control channel, authorization evidence, and actions Mudi can
safely offer for that Run.

Three capability levels must not be conflated:

1. **Observe** - discover the Session, resolve its Project and Worktree, and show supported
   metadata without claiming control.
2. **Associate** - explicitly link the Session to a managed execution without guessing its
   goal or taking over its live process.
3. **Control** - start or resume a Current Run through a Mudi-owned control channel
   and offer only actions covered by current authorization and conclusive process evidence.

It remains undecided whether an externally started, currently Open Session can participate
directly in managed execution, whether it must first produce a manual Result, or whether
Mudi should continue through a managed Successor Session instead.

One proposed bridge is an explicitly authorized Handoff into a Mudi-owned private
tmux environment:

```text
externally started Session A
  -> authorized Handoff Result
  -> Mudi starts Session B in its private tmux environment
  -> Session B continues the work as a distinct Successor Session
```

This transfers working context, not Session identity or transcript. Session A remains the
external worker; Session B is a distinct worker whose Current Run was launched inside the
Mudi-managed environment. The two Runs can safely expose different actions because
Mudi has different launch, liveness, and control evidence for them.

This proposal originally conflicted with ADR 0003 because managed 2.0 Sessions require
private tmux. ADR 0009 resolves that conflict for Managed Current Runs by partially
superseding ADR 0003's rejection of a required tmux dependency while preserving the
existing Operation Task guarantees. Choosing Action-bounded non-interactive Current Runs
removes the need for Mudi to inject Action prompts into a long-running Provider TUI:
it can launch the complete Provider command as one tmux-managed process. Direct terminal
input is reserved for a Developer-owned interactive Run. Only a validated structured
Result may advance a Flow.

## Embedded managed terminal hypothesis

A private tmux environment could make the currently empty Session Workspace a live view of
the selected managed Session. While Automation-owned, it shows the current or latest
non-interactive Run as a read-only terminal preview. `Take Control` starts or resumes an
interactive Provider Run and enables developer input so the developer can type prompts,
answer interactions, or use terminal programs directly.

```text
Project and Session tree       selected managed Session
+----------------------+      +------------------------------------------+
| Project              |      | Current Run rendered from private tmux |
|  `-- Session B       |      |                                          |
|      Busy            |      | > user can focus and type here           |
+----------------------+      +------------------------------------------+
```

The current Rust TUI does not yet provide this capability. It uses Ratatui and Crossterm
for one alternate-screen application, but has no tmux client, embedded VT terminal
emulator, pane-resize coordination, or complete keyboard, paste, mouse, and escape routing.
The feature is feasible, but it is a terminal-client subsystem rather than a normal text
widget.

Direct developer input requires exclusive Input Ownership so the scheduler and developer
never type into the same pane concurrently:

- **Automation-owned** - Mudi may dispatch declared Actions. The terminal can be
  viewed read-only without changing ownership.
- **Take Control** - an explicit operation pauses the Flow path affected by this Session,
  waits until input dispatch is at a safe boundary, transfers ownership, and enables
  developer input.
- **Developer-owned** - the developer may interact directly; Mudi cannot dispatch
  input to this Current Run. Independent Flow paths may continue.
- **Return to Flow** - an explicit operation disables developer input and makes
  Mudi revalidate Session, Worktree, Action, and plan state before restoring
  Automation ownership. Leaving terminal focus or detaching from tmux never implies
  return.

`mudi attach` performs `Take Control` before attaching an external terminal. If the
developer bypasses Mudi and attaches directly with tmux, detection of that attached
client conservatively pauses the affected path; detaching still does not restore
Automation ownership.

## Strong objections and risks

### A second source of product truth

An internal Work Item model can drift from GitHub Issues and repository PRDs. Mudi
should own execution truth, not silently duplicate priority, requirement, or issue state.

### Skill outputs are not Mudi domain objects

Agent Skills own the interpretation, synthesis, and publication of Spec and Tickets.
Reimplementing that logic in Mudi would duplicate Agent capability and couple the
control plane to document formats. Reliable scheduling still requires explicit result
references and dependency evidence; it must not depend on Mudi interpreting the
prose itself.

### Moving specifications

If an ADR or PRD changes during a Workflow Run, different Sessions may execute different
requirements. The current recommendation is to pin exact external artifact revisions at
start, pause affected future Steps when they change, and require an explicit Plan Revision.
This has not been confirmed.

### Authorization expansion

ADR 0002 rejects unattended or blanket control. A multi-step Workflow Run needs a new,
precise authorization boundary: one approval may cover a completely declared plan, but it
must not become persistent authority over an entire Project. Whether this extends or
replaces the existing Control Operation model remains unresolved.

### Provider asymmetry

Codex app-server exposes structured Thread, Turn, Item, approval, diff, and completion
events, but it is Codex-specific and currently experimental. Claude Code does not
automatically provide an equivalent control protocol. A provider-neutral UI must not imply
provider-neutral control guarantees that do not exist.

### Ownership and recovery cost

Once Mudi starts Sessions, handles approvals, and advances dependent Steps, it owns
durable scheduling and recovery responsibilities. Process ambiguity, partial side effects,
stale approvals, conflicting Worktrees, and interrupted result publication become core
product behavior rather than edge cases.

## Open decisions

1. Does a Workflow Run pin exact revisions of its external Spec, ADR, and Ticket inputs, or
   can it follow changes to those artifacts?
2. Does an approved Ticket dependency graph become the Execution Plan directly, or does
   Mudi transform it into a separate execution representation?
3. What is the smallest useful structured Result contract, and how does it vary by Action
   type?
4. Can one Session receive multiple Assignments, or is one Session one execution attempt?
5. Can multiple Sessions work on one Step concurrently, and how are competing Results
   accepted or rejected?
6. What exact permissions, deadline, cancellation behavior, and recovery rules bound one
   `Start Flow` authorization?
7. Must every managed execution stay inside one Project? If not, where is cross-Project
   authority expressed?
8. How are externally started Sessions attached to managed execution without guessing?
9. Which Worktree isolation and integration policies are required for sequential and
   parallel Steps?
10. Which Codex-specific app-server capabilities, if any, should Mudi expose as
    optional enhancements without making managed execution depend on them?
11. If a daemon hosts scheduling, what TUI heartbeat or control-lease rule makes an
    unclean TUI loss pause further dispatch consistently with normal exit?
